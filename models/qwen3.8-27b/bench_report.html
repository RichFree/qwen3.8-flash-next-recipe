Part 2 — concurrency sweep (1× / 2× / 4×, all four depths)

Data‑integrity note. The sonnet dataset used for realistic text deterministically tiles the same small corpus regardless of requested depth — so a 65,536‑token prompt is a literal prefix‑extension of the 16,384‑token prompt already served earlier in the same sweep, on the same long‑lived server. vLLM's automatic prefix caching (on by default, as it would be in production) turned that into a spurious 8× "speedup" for one cell (spec, 2×, depth 65,536: TTFT measured at 1.2s). We caught it via the /metrics prefix‑cache‑hit counters, then re‑ran that cell in isolation against a freshly‑restarted, cache‑empty server (0 hits confirmed) to get the corrected TTFT of 15.9s used below. One neighboring cell (spec, 4×, depth 16,384, flagged in the table) shows a milder version of the same pattern and should be read with the same caution — its decode throughput numbers are unaffected either way, since prefix caching never shortcuts token generation, only prompt prefill.

Spec‑decode speedup vs. concurrency, by depth

Per‑request decode tok/s ratio (spec ÷ no‑spec). Dashed line = break‑even (1.0×, spec decode provides no benefit).

The speedup from speculative decoding is largest at single‑stream concurrency and shallow depth (2.3× at depth 1,024) and erodes steadily as either concurrency or context depth increases — dropping toward ~1× (no benefit) at depth 65,536 with 4 concurrent requests. This matches the expected mechanism: dflash's gain comes from trading idle memory‑bandwidth for compute during single‑request decode; once the batch is large enough that the GPU is already compute‑bound generating real tokens for other sequences, the draft model's extra verify‑step FLOPs compete directly with that useful work instead of being free. Meanwhile, aggregate throughput itself scales well with concurrency regardless of spec decode — ~2.6–3.3× going from 1× to 4× concurrency at shallow depth, tapering at 64K depth where per‑request KV‑cache size starts to dominate.
